# 〇、深圳规则生效日的确定结论

> **深圳条例第十八条第二款对应规则的 `provision_effective.from` 应当填写 `"2008-11-01"`，不得填写 `"2019-04-24"`。**

理由：

1. 《深圳经济特区和谐劳动关系促进条例》原始文本于 2008 年 9 月 23 日经深圳市第四届人民代表大会常务委员会第二十二次会议通过，自 2008 年 11 月 1 日起施行；
2. "用人单位与劳动者协商延长劳动合同期限累计超过六个月的，视为续订劳动合同"这一规定，在 2008 年原始文本中就已经存在；
3. 2019 年 4 月 24 日经市六届人大常委会第三十三次会议通过的，是《关于修改〈深圳经济特区医疗条例〉等二十七项法规的决定》，属于二十七项法规的打包技术性修正，主要修改主管部门名称、删除原第七十一条等内容，**没有修改第十八条第二款**；
4. 2019 年 4 月 24 日是修改决定的通过日，不是这项实体规则的初始生效日。

因此不只是改一个日期，还应当顺手把数据模型改严谨。

# 二、《解释二》第十一条必须升格为第一版核心规则

最高法正式文本规定，劳动合同期满后劳动者继续工作、用人单位未表示异议超过一个月的，可以产生三个递进后果：

1. 请求按照原条件续订劳动合同
2. 已符合无固定期限劳动合同条件的，请求按照原条件订立无固定期限劳动合同
3. 用人单位后来解除的，请求其承担解除劳动合同的法律后果

这一规则是在通过"拟制续订"解决合同期满后继续用工的解除、终止问题，防止用人单位在继续用工一段时间后仍任意援引原到期日结束劳动关系。

但施工时必须注意：

> **第十一条不能编码成"继续工作超过一个月＝违法解除＝2N"。**

它解决的是：

* 原合同到期后劳动关系是否继续
* 是否产生拟制续订
* 后续应当按照"解除"还是原合同"自然到期终止"审查

公司后来解除是否合法，仍然要审查公司提出的解除依据和程序。

# 三、问题树的准确补丁

**round2 的 A15 整条删除**，替换成以下分支。

## A15：合同到期后是否继续实际工作？

```text
○ 没有，到期后即停止工作
○ 有，仍然正常工作
○ 有，但只工作了几天或处于交接状态
○ 不确定
```

**为什么必须问：** 它决定是否进入《解释二》第十一条，而不只是普通合同到期终止。

路由：

```text
没有        → 继续普通到期路径
正常工作     → A15.1
只是短期交接  → A15.2
不确定       → 事实不足提示
```

## A15.1：公司最早在什么时候明确表示不同意你继续工作或不同意续订？

```text
○ 合同到期前已经明确表示
○ 到期后一个月以内明确表示
○ 到期超过一个月后才明确表示
○ 到现在仍未明确表示
○ 公司说过不续签，但之后仍持续安排我工作
○ 不确定
```

**为什么必须问：** 第十一条要求的是用人单位"未表示异议超过一个月"。

这里不能只问"公司有没有通知"，还要捕捉一种非常常见的矛盾状态：

> 公司到期前口头或书面说不续签，但到期后继续安排工作、考勤和发薪。

这种情况下，不能机械地因为存在一句"不续签"就排除第十一条，应当输出事实冲突和专业复核提示。

## A15.2：到期后继续工作的状态是什么？（多选）

```text
□ 公司继续安排任务
□ 公司继续要求考勤
□ 公司继续支付工资
□ 公司继续进行绩效或工作管理
□ 我继续使用公司账号和系统
□ 只是处理离职交接，没有继续承担正常工作
□ 以上都不确定
```

**为什么必须问：** 它改变"仍在用人单位工作"的证据状态。用于区分：真正继续履行劳动合同／仅仅短期交接／只有劳动者单方留在工作场所／回答存在冲突。

## A15.3：未表示异议的时间是否超过一个月？

由系统根据日期计算，不让用户自己判断。

输入：

```text
原劳动合同到期日：
公司首次明确表示异议的日期：
```

公司一直未表示异议的，以当前日期计算。

### 技术上必须注意

不要写：

```ts
days > 30
```

法条写的是"超过一个月"，应当按**日历月**判断。依据为《民法典》第二百零二条（按年、月计算期间的，以到期月的对应日为最后一日；没有对应日的，以该月月末日为最后一日），该依据必须登记进 `legal_basis`。

```ts
const thresholdDate = addOneCalendarMonth(contractExpiryDate);

const exceedsOneMonth =
  objectionDate === null
    ? currentDate > thresholdDate
    : objectionDate > thresholdDate;
```

月底边界测试：

* 1 月 31 日 → 2 月 28 日
* 1 月 31 日 → 3 月 1 日
* 8 月 31 日 → 9 月 30 日
* 8 月 31 日 → 10 月 1 日

## A15.4：现在的状态是什么？

```text
○ 目前仍在继续工作
○ 公司后来书面通知我离开
○ 公司后来口头要求我离开或关闭权限
○ 我自己提出了离职
○ 已经不再工作，但无法确定是谁结束的
```

**为什么必须问：** 它决定第十一条对应的三种输出：

```text
仍在工作          → 原条件续订候选
符合无固定期限条件  → 原条件订立无固定期限合同候选
公司后来结束劳动关系 → 解除法律后果审查
```

## A15.5：公司后来结束劳动关系时写的理由是什么？

```text
○ 原劳动合同早已到期
○ 客观情况发生重大变化
○ 严重违纪
○ 不能胜任工作
○ 协商解除或个人辞职
○ 没有书面理由
○ 其他
```

**为什么必须问：** 第十一条不能单独判断后续解除是否合法。它只能把案件从"原合同在最初到期日自然终止"推进为"劳动关系已经续存，后来发生了另一次解除行为，需要审查解除依据和法律后果"。

# 四、第十一条与第十条必须并行运行

不能设计成"命中第十条→停止检测第十一条"。正确结构：

```text
固定期限合同历史检测
├── 实际签署两次
├── 协商延长
├── 自动续延
├── 变换主体
└── 其他诚信规避

合同到期后状态检测
└── 继续工作且单位未异议超过一个月
```

规则可以叠加：

```text
CN-SPC-LABOR-II-10-1
+
CN-SPC-LABOR-II-11
+
CN-LCL-14-2-3
```

例如：已经连续订立二次固定期限劳动合同；第二次合同期满后继续工作超过一个月；公司未表示异议；劳动者要求按照原条件订立无固定期限劳动合同。这会比单独命中第十条更强。

# 五、新增三个输出模板

## C20：期满后继续工作超过一个月

```text
## 规则命中：劳动合同期满后可能已经进入拟制续订状态

你填写的事实显示：

- 固定期限劳动合同已经到期；
- 到期后你仍然继续正常工作；
- 用人单位未表示异议超过一个月。

根据当前规则，你可以重点评估是否请求用人单位按照原劳动合同条件续订劳动合同。

### 最高优先级 Warning

不要再把劳动关系结束日期当然写成原劳动合同到期日。

如果合同到期后双方仍持续安排工作、考勤、发薪和接受管理，真正需要审查的可能是：

公司后来在什么时间、以什么理由结束了继续存续的劳动关系。

### 现在应当固定

- 原劳动合同及到期日期；
- 到期后的考勤记录；
- 到期后的工资支付记录；
- 到期后公司安排的任务；
- 公司首次表示不同意继续工作的具体日期和原文。

### 不确定性

"是否超过一个月"可以根据日期计算。

"是否属于继续正常工作"以及公司是否已经通过明确行为表示异议，仍可能依赖个案事实。
```

## C21：继续用工叠加无固定期限合同条件

```text
## 规则叠加：可能有权请求按照原条件订立无固定期限劳动合同

你填写的事实同时显示：

1. 劳动合同期满后继续工作；
2. 用人单位未表示异议超过一个月；
3. 你可能已经符合订立无固定期限劳动合同的条件。

在这些事实成立的情况下，可以重点评估是否请求用人单位按照原劳动合同条件订立无固定期限劳动合同。

### 最高优先级 Warning

不要只把案件表述为普通合同到期并要求经济补偿。

真正的核心争点可能是：

- 劳动关系是否已经拟制续订；
- 用人单位是否负有订立无固定期限劳动合同的义务；
- 公司后来结束劳动关系属于何种解除；
- 应当选择继续履行还是赔偿金。

### 当前不应直接主张

- 不应仅凭"继续工作超过一个月"直接断言一定获得2N；
- 不应把继续履行和赔偿金作为可以同时累加的最终法律后果；
- 不应忽略劳动者本人是否愿意续订以及是否存在法定排除事由。
```

## C22：继续用工后公司再通知离开

```text
## 当前更接近：劳动关系续存后的解除，而不是原到期日自然终止

你填写的事实显示：

- 原固定期限劳动合同到期后，你继续正常工作；
- 用人单位未表示异议超过一个月；
- 此后用人单位又通知你停止工作或者离开公司。

这次操作不宜直接按照原劳动合同到期日处理。

需要进一步审查：

- 公司后来解除劳动关系的具体日期；
- 公司当时写明的解除理由；
- 该理由是否具备法律依据；
- 公司是否履行相应程序；
- 你选择继续履行还是赔偿金路径。

### 最高优先级 Warning

不要在仲裁申请中只写：

"劳动合同到期，公司不再续签。"

这种写法可能遗漏合同到期后继续用工以及后来解除这两个关键事实。

### 当前结论

《劳动争议解释二》第十一条支持将公司后续行为放入解除法律后果中审查，但本规则本身不直接证明该解除必然违法。
```

# 八、引用体系必须独立成一个 `sources.yml`

这个项目不能允许"法条内容正确，但链接随便找了一个政府镜像"，因为它的信誉恰恰建立在"规则可核验"上。

把 URL 从每条规则里抽离，建立唯一的来源注册表：

```yaml
sources:
  - id: "SPC-LABOR-II-2025"
    publisher: "中华人民共和国最高人民法院"
    authority_level: "national-judicial"
    page_title: "关于审理劳动争议案件适用法律问题的解释（二）"
    official: true
    url: "..."
    pinpoint:
      - "第十条"
      - "第十一条"
    page_opened_and_checked: false
    last_verified_at: ""
    verified_by: ""
    status: "active"

  - id: "SZ-HARMONIOUS-LABOR-2008"
    publisher: "深圳市人民代表大会常务委员会"
    authority_level: "special-economic-zone-legislation"
    page_title: "深圳经济特区和谐劳动关系促进条例"
    official: true
    url: "..."
    pinpoint:
      - "第十八条第二款"
    page_opened_and_checked: false
    last_verified_at: ""
    verified_by: ""
    status: "active"
```

每条规则只写：

```yaml
legal_basis:
  - source_id: "SPC-LABOR-II-2025"
    article: "第十一条"
```

不要在二十个规则文件中重复维护同一个 URL。

## 构建时强制检查

```text
每条legal_basis必须存在source_id
source_id必须在sources.yml中存在
official必须为true
page_opened_and_checked必须为true
last_verified_at不能为空
pinpoint必须包含对应条文
status不是active时构建失败
```

## 不能自动检查的部分

程序能检查：链接格式、域名、页面是否返回、source ID 是否存在。

程序不能真正检查：页面是不是对应法规、条文是不是最新版、链接内容有没有被错误理解。

所以必须保留固定人工工序：

> **每条法律依据的官方原文页，维护人亲自打开一次，核对页面标题、制定机关、条文、施行日期和修改沿革。**

外链可用性检查可以自动跑，但不建议因政府网站临时无法访问就阻止部署；语义核验永远是人工责任。

# 九、前置验证拆成两阶段

> **"决定做不做"和"已经决定做以后建立规则资产"不是一件事。** round2 把全量案件编码提前到了立项前，容易让项目死在开工前。

## 第一阶段：一小时，决定是否开工

不要读卷。只根据对案件的记忆、首次咨询记录或现成案件概览填 10 行，六列：

| 案件编号 | 当事人第一次判断错了什么 | 真正改变定性的事实 | 最小 Warning | 如果早两周看到，是否会改变一个动作 | 会改变什么动作 |
| --- | --- | --- | --- | --- | --- |
| P01 | 以为到期不续签只有 N | 实际已经签过两次固定期限 | 检查是否存在无固定期限订立义务 | 是 | 不会只按 N 主张 |
| P02 | 以为 AI 替岗属于合法裁员 | 公司只谈补偿，未谈具体岗位 | 只谈离职不等于协商变更合同 | 是 | 会要求公司提出具体岗位 |
| P03 | 以为原合同到期即结束 | 到期后继续工作两个月 | 不要把原到期日写成关系结束日 | 是 | 会保留后续工作和发薪证据 |

每案最多六分钟。

### 开工判据

1. 十个案件里，是否至少有五六个会因为提前看到 Warning 而改变一个具体动作？
2. 这些 Warning 是否集中在两三个重复结构中？
3. 这些 Warning 能否通过少量客观问题触发，而不必先完整阅卷？

三个答案大体为"是"，就开工。

如果只有"用户都不懂劳动法"，但错误各不相同、每案都必须完整阅卷，就写文章，不做工具。

## 第二阶段：决定做以后全量编码

这时才把一二十个案件全部按 round2 第一节的九字段编码。它已经不再是验证成本，而是在建设问题树、规则库、Warning 文案、测试样本、证据模型和 Case Export。两三天是合理成本，而且这部分最终会留在 repo 里形成真正资产。

# 十、工时按 45—60 小时准备

round2 的 29 小时只能理解为"页面能跑起来、规则能够初步输出"，没有充分计入法律来源逐条核验、日期边界、问题树矛盾检查、输出文案压缩、真实案件回放、盲测、手机端、Case Export 修订、README 和开源文档、规则版本管理。

| 阶段 | 工时 |
| --- | ---: |
| 一小时立项验证 | 1 |
| 全量案件编码 | 8—12 |
| 法律规则及来源核验 | 8—10 |
| 问题树、Finding 和文案 | 8—10 |
| 页面开发 | 10—14 |
| Case Export 及规则详情 | 4—6 |
| 自动测试、案件回放、盲测修正 | 8—10 |
| README、部署及最终检查 | 3—5 |
| **总计** | **50—68** |

在 AI Coding 配合顺畅、范围不扩张的情况下，压到 45—60 小时有可能。但不再把"20—30 小时"写成项目总预算，避免开发到第三天时产生"是不是做错了"的虚假挫败。

# 十一、开工顺序

```text
1小时十行清单
↓
决定做
↓
全量案件编码
↓
加入《解释二》第十一条
↓
建立sources.yml并逐条人工核验
↓
冻结20条法律测试
↓
冻结问题树和全部输出文案
↓
最后才创建React项目
```

> **这个项目最大的风险不是做不出来，是卡在开工前。**

现在不需要继续完善战略，也不需要继续想名称、Logo 或技术架构。第一项工作的定义已经非常清楚：

> 从手上一二十个程序员案件中快速挑十个，每案写一行：
> **"如果这个人在第一次找我前两周看到哪一条 Warning，他会不会改变一个具体动作？"**

只要这十行里出现明显重复，项目就正式启动。
