按已锁定的边界，这个产品不是"帮用户算能拿多少钱"，而是：

> **一个纯前端、规则显式、结论不完备的劳动关系操作 Linter：在用户签字、回复公司或提交仲裁请求前，发现可能改变法律定性的 warning。**

它的核心价值不是替用户"判断胜负"，而是阻止用户把尚可修正的问题，变成个人辞职、错误诉请、证据灭失或者时效届满等不可逆事实。

# 一、对三处质疑的回应

## 甲：把"反向清单"当核心，是不是高估了用户的理解意愿？

**没有高估它的重要性，但高估了普通用户愿意阅读一张完整反向清单的耐心。**

所以应当：

> **核心逻辑保留，核心呈现压缩。**

用户完成问答后，结果页第一屏不要先出现一堆"不要主张什么"，而应当只出现一条：

### 最高优先级 Warning

例如：

> **你现在最不该做：只以"N"提交仲裁申请。**
>
> 你的合同续订历史可能触发"连续订立二次固定期限劳动合同"的规则。如果最终属于违法终止，只主张经济补偿可能与实际法律路径不一致；而诉请一旦进入仲裁程序，后续调整可能受到限制。

下面最多再显示三条：

* 不要把个人辞职写进任何文件；
* 不要同时把继续履行与 2N 作为可累加项目；
* 不要等解除后再回头找内部续签和岗位证据。

也就是说：

* **反向清单应当是规则引擎的核心；**
* **但前台不能做成长篇"错误大全"；**
* 每次只输出与当前分支直接相关的 **1 个主警告 ＋ 最多 3 个次警告**。

而且本产品根本不输出赔偿数字，所以"用户只看数字就走"不是主要问题。更现实的问题是：用户只想知道"我现在该干什么"。反向清单必须翻译成具体动作，而不是法律术语。

## 乙：纯前端零留存，怎么判断有没有真的被使用？

必须说得很诚实：

> **无后端、无埋点、无上报，就无法可靠知道多少人完成了问答、走了哪个分支、复制了几次报告。**

不能一边承诺绝对零遥测，一边又幻想得到完整漏斗数据。这两件事不能同时成立。

但仍然可以观察三类信号。

### 1. 传播与访问层

GitHub 自带的 Repository Insights 可以看到最近 14 天的访客、完整 clone、来源网站和热门内容，但它主要反映 repo 的访问与传播，不能证明用户完成了网页诊断。[1]

可观察：

* Repo unique visitors
* Stars、Forks、Watchers
* Clone 数量
* V2EX、HelloGitHub、周刊等来源
* 发布帖浏览、收藏、评论
* 自然出现的二次转发和第三方介绍

### 2. 用户主动留下的行为证据

结果页可以放两个完全自愿的按钮：

* `报告规则错误`
* `这个问题没有被覆盖`

点击后打开 GitHub Issue Form，不自动带入用户答案，只预填工具版本和规则 ID。GitHub 的 Issue Form 可以通过 YAML 配置下拉框、复选框和结构化字段，适合做自愿反馈。[2]

Issue Form 第一行必须写：

> 请勿提交公司名称、姓名、聊天记录、劳动合同、源代码、客户信息或其他敏感材料。

此外，Case Export 固定带上：

```text
Generated by Employment Linter CN
Tool version: 0.1.0
Ruleset version: 2026-09-03
```

未来用户把报告发给你咨询时，你自然知道：

* 他确实完成了工具
* 使用的是哪个版本
* 哪个入口产生了咨询
* 报告是否真的降低了首次沟通成本

这不是暗中追踪，而是用户主动把产物交给律师。

### 3. 人工验证层

在 v0.1 阶段，真正有意义的"完成率"和"理解率"只能通过小规模人工测试获得：

* 找 5—8 名程序员实际使用
* 让他们共享屏幕完成
* 不提示答案
* 观察在哪一步退出或误解
* 完成后要求他们用自己的话回答：
  * 公司这次操作可能属于什么
  * 现在最不能做什么
  * 下一步要保存什么
  * 自己准备主张什么

结论：

> **v0.1 坚持零埋点是对的，但必须接受线上真实完成率不可见。**
>
> 线上看传播，人工测试看可用性，Case Export 回流看商业价值。

不要拿 Star 当使用量，也不要拿 Repo Visitor 当诊断完成量。

## 丙：抽 8—10 个案件，每案写一行错误，重复度高就做，够不够？

**不够。**（注：本节的分阶段安排已被 round3 第九节修订，以 round3 为准。）

它足以发现一个假设，但不足以决定做产品，因为它只验证"错误有没有重复"，没有验证三个更重要的问题：

1. 这个错误是否会导致实际损害
2. 能否通过有限问题纠正
3. 工具是否可能在没有律师阅卷的情况下给出安全 warning

每案至少记录以下九项：

| 字段 | 内容 |
| --- | --- |
| 案件编号 | 仅用匿名编号 |
| 公司操作形态 | 到期不续签／40 条第 3 项／协商解除／事实解除 |
| 当事人最初判断 | 他第一次联系你时怎么理解 |
| 真正关键分叉 | 哪个事实改变了定性 |
| 判断错误原因 | 不知道规则／误解文件／漏掉事实／诉请选择错误 |
| 可能造成的损害 | 少主张／签错文件／证据灭失／错过时效 |
| 最小纠错问题 | 只问哪一个问题就可能让他意识到错误 |
| 是否需要阅卷 | 无需／简单看文件／必须全面审查 |
| 工具是否可纠正 | 可以／只能预警／不能 |

前置验证不应只看"重复率"，而应看：

> **重复度 × 行动价值 × 可规则化程度。**

### 可以做网页工具

同时满足：

* 前两类错误覆盖全部样本的 **60% 以上**
* 至少有 **5 个案件**，如果当事人更早看到 warning，会改变签字、续订表态、诉请选择或证据固定行为
* 目标案件中至少 **80% 可以在 15 个以内的实际可见问题中完成初步分流**
* 不能自动判断的案件能够稳定进入"停止自动判断／建议复核"，而不是给出错误安慰
* 用未参与规则编写的 3—5 个留置案件测试，分类候选没有出现严重漏报

### 更适合写文章

出现以下任一情形：

* 错误重复，但每案必须阅读劳动合同、解除通知和大量聊天记录才能识别
* 问题树必须超过 25 个问题才能避免误导
* 相同输入在现有裁判实践下仍无法形成稳定 warning
* 产品只能告诉用户"情况很复杂，建议咨询律师"
* 错误只是知识缺口，并不改变当事人的下一步行为

最关键的一条不是"重复了几次"，而是：

> **这个工具是否能在某个不可逆动作发生之前，改变用户的一项具体行为。**

# 二、产品的基础架构：不是一棵树对应一个结论

不要把产品实现成：

```text
回答A → 结论A
回答B → 结论B
```

真实案件可能同时命中：

* 自动续延
* 变更签约主体
* 未实质协商调岗
* AI 替岗只是内部经营调整
* 当事人已经错写了仲裁请求

因此最终结果应由四个模块组合：

```text
结果页
├── A. 定性候选：可以同时出现多个 Finding
├── B. 主张路径：只能形成一个当前优先方向或停止判断
├── C. 证据固定：按案件形态生成
└── D. Case Export：汇总全部输入与 Finding
```

例如：

```text
C08 深圳协商延长视为续订
+
C12 续订意愿证据不足
+
R03 暂不建议提交仲裁请求
+
P01 合同到期证据固定清单
```

这比为所有排列组合分别写几十个"终点页面"稳得多。

# 三、先固定四条法律护栏

## 1. "符合二次固定期限"不能直接等同于 2N

《劳动争议解释二》第十条解决的是"是否视为连续订立二次固定期限劳动合同"；之后还要继续判断：

* 劳动者是否提出或者同意续订
* 是否明确要求继续签固定期限
* 是否存在劳动合同法第三十九条、第四十条第一项或第二项情形
* 最终是否违法终止
* 劳动者选择继续履行还是赔偿金

所以问题树不能写成：

```text
延长一年 → 2N
```

而必须是：

```text
延长一年
→ 视为二次固定期限
→ 是否提出或同意续订
→ 是否存在法定排除事由
→ 是否产生订立无固定期限合同义务
→ 到期终止是否存在违法终止候选
→ 继续履行或赔偿金路径
```

最高法司法解释明确列出四类视为二次固定期限的情形；劳动合同法第十四条则同时要求续订意愿并规定排除情形。[3]

## 2. 深圳必须设置独立地域规则

全国规则是协商延长期限累计达到一年以上；深圳现行特区条例规定，协商延长累计超过六个月即视为续订。

因此：

* 深圳超过 6 个月但不足 1 年：命中深圳地方规则
* 达到 1 年：同时命中深圳规则和全国司法解释
* 结果页必须同时展示命中的依据，不要悄悄用一个覆盖另一个
* 6—12 个月区间标注为"深圳规则命中"，但后续违法终止结论仍要经过续订意愿、排除事由和个案审查

## 3. 第 40 条第 3 项必须拆成四层

```text
客观情况发生重大变化
→ 导致原合同无法履行
→ 进行过真实的合同变更协商
→ 未能达成协议
→ 30日书面通知或额外支付一个月工资
```

劳动合同法第四十条第三项明文要求"无法履行"和"协商未果"两项前提。

广州魏某案和杭州 AI 替岗案反映出的审查方向是：企业主动引入 AI、降低成本或者内部组织调整，并不当然构成外部、不可预见的客观情况；仅谈补偿或提出明显降薪的岗位，也不能当然等同于真实、合理的合同变更协商。[5]

这些案例只能作为裁判思路和解释信号，不能编码成：

```text
reason == AI
=> unlawful
```

## 4. 主张选择必须放在结果生成之前

劳动合同法第四十八条规定的是两种替代性法律后果：

* 要求继续履行
* 不要求继续履行或者已经不能继续履行时，要求赔偿金

违法解除、终止赔偿金为经济补偿标准的二倍。解释二还列出了可能认定为"已经不能继续履行"的情形，并规定可继续履行时的期间工资。

劳动仲裁一般时效是一年，但存在中断和中止；进入诉讼后新增请求，只有与原争议不可分时才可能合并处理，独立请求通常仍要先仲裁。

因此产品不能把"写申请书"放在前面，而要先问：

> 你究竟想回去，还是想结束关系并要求赔偿？

# 四、完整问题树

## 4.1 第一屏全文

```text
# 在签字、回复公司或提交仲裁请求前，先跑一次检查

这不是赔偿计算器，也不会判断你一定能赢。

它只检查三类问题：

1. 固定期限合同到期，是否可能被错误地当作普通不续签；
2. AI替岗、团队缩编或岗位取消，是否真的满足"客观情况发生重大变化"；
3. 违法解除或终止后，你是否可能选错了继续履行、赔偿金或经济补偿的主张路径。

你的回答仅保存在当前页面状态中。

无账户。
无后端。
无文件上传。
无分析埋点。
运行时不调用大模型。

关闭或刷新页面后，未导出的内容将不会由本工具保存。
静态托管平台仍可能按照其自身政策记录基础访问日志，但你的问答内容不会被本工具发送。

## 公司这次正在做什么？

○ 固定期限劳动合同到期，公司明确不续签或可能不续签
○ 公司以AI替代、团队缩编、岗位取消、业务调整等理由单方解除
○ 公司提出协商解除，或要求我写个人辞职、签离职文件
○ 没有明确书面通知，但已经不让我工作、关闭权限、停发工资或要求离开
○ 我收到了一份书面文件，但看不出它属于哪一种
```

这一屏没有律师身份、微信、咨询入口，也没有"立即测算 2N"。

## 4.3 固定期限合同到期路径

| 编号 | 问题及选项 | 为什么必须问 | 路由 |

| A09 | 连续工作期间，劳动合同签约主体是否被更换？`是／否／不确定` | 对应解释二第十条第三项 | 是→A10 |
| A10 | 下列四项是否同时成立：`并非你主动要求换主体；工作场所基本相同；岗位或核心职责基本相同；实际管理、考核或汇报关系持续` | 四项决定是否命中变换主体规则 | 全部成立→C10；部分成立→C12 |
| A11 | 是否存在其他可能为规避无固定期限合同而安排的做法？`被要求先个人辞职后立即重签；形式上短暂停工但实际工作连续；反复更换合同名称或主体但工作不变；公司明确提及避免无固定期限；其他；均无` | 对应第十条第四项，但需要个案和诚信判断 | 有→C11 |
| A12 | 在到期前或到期时，你是否明确表示愿意继续工作、续订合同？`有书面表达／只有口头表达／没有表达／明确拒绝续订／不确定` | 第十条只解决"第二次合同"，无固定期限订立义务还涉及劳动者续订意愿 | 书面→继续；口头或不确定→C12；拒绝→通常不进入违法终止候选 |
| A13 | 你是否明确要求"仍然只签固定期限合同"？`是／否／不确定` | 劳动者主动要求固定期限是第十四条中的例外 | 是或不确定→C12 |

| ~~A15~~ | **本条作废，见 round3 第三节** | — | — |
| A16 | 仅在未触发二次固定期限规则时出现：公司是否提出以维持或提高原条件续订，而你拒绝？`是／没有提出／提出但降低条件／不确定` | 决定普通到期终止是否存在经济补偿候选 | 是→C05；否则→C04 |

### 到期路径的关键设计

四类"视为二次固定期限"的情形必须**并行检测**，不能命中一个就停止。一个案件可能同时存在延长期限和变换签约主体。

# 五、结果生成逻辑

程序不应采用"命中第一个结果就 return"的逻辑，而是：

```ts
const findings = evaluateAllApplicableRules(facts);

const primaryFinding = selectPrimaryFinding(findings, {
  first: "BLOCKER",
  second: "ERROR",
  third: "WARNING",
  fourth: "INFO",
});

const claimModule = resolveClaimPath(facts, findings);
const evidenceModule = resolveEvidenceChecklist(facts, findings);
const complexity = resolveComplexityByTriggers(facts, findings, claimModule);
```

## 高复杂度不是积分，而是触发式判断

满足任一项即为 `HIGH`：

* 已签协商解除协议或提交个人辞职
* 已经提出仲裁请求，但与当前建议方向不一致
* 仲裁时效可能届满
* 希望继续履行，但存在可能无法继续履行的情形
* 深圳 6—12 个月延长合同规则成为关键依据
* 规避无固定期限合同涉及诚信判断
* 事实解除证据存在冲突
* 同时出现两种以上互相竞争的解除定性
* 关键事实只有口头陈述，没有任何书面材料
* 进入 v0.1 未覆盖的 39 条、40 条第 1/2 项、法定续延等路径

不要做"复杂度 78 分"之类的伪精确评分。

# 六、不确定性标注体系

## 6.1 四档不是胜诉概率

| 档位 | 含义 | 界面标签 | 标准措辞 |
| --- | --- | --- | --- |
| Deterministic | 日期、期限、是否存在文件等可由输入直接计算或确认 | `D · 可计算` | "根据你填写的日期，协商延长期限累计为……" |
| Rule-based | 明确规则的构成条件表面命中 | `R · 规则命中` | "若你填写的事实与原始材料一致，该规则的明示条件已被触发。" |
| Fact-sensitive | 定性取决于证据内容、真实性、前后关系和反方证据 | `F · 依赖个案事实` | "当前事实支持这一候选，但通知原文、沟通记录或相反证据可能改变判断。" |
| Judicial discretion | 合理性、诚信、是否无法履行等没有唯一机械阈值 | `J · 存在裁量` | "该问题没有单一数值标准，不同裁审者可能根据整体事实作出不同评价。" |

## 6.2 结果档位取最高不确定性

一项规则本身可能是 `rule-based`，但用户只有口头回忆，此时最终展示不能仍是规则判断。

```text
最终不确定性
=
规则本身的不确定性
与
输入证据的不确定性
两者中的较高者
```

例如：

```text
深圳延长期限超过六个月
规则层：R · 规则命中

但用户记不清延长日期，也没有协议
最终：F · 依赖个案事实
```

## 6.3 严重程度与不确定性必须分开

下面两条可以同时成立：

```text
BLOCKER · FACT-SENSITIVE
```

意思是：

* 这个问题会阻止自动给出主张建议
* 但它仍然依赖事实，不是已经被证明

严重程度：

* `BLOCKER`：必须停止自动判断
* `ERROR`：已发现与目标路径明显冲突的输入
* `WARNING`：可能改变结论的重要问题
* `INFO`：规则说明或已确认事实

## 6.4 证据覆盖状态

不要写"证据充分""足以胜诉"，只写：

* `有直接材料`：用户确认持有原始通知、合同、邮件等
* `有间接材料`：只有聊天转述、截图片段、同事证明等
* `仅有本人陈述`
* `尚未取得`
* `答案存在冲突`

## 6.5 明确禁止的表达

产品中禁止出现：

```text
你一定能拿2N
稳了
稳赢
100%违法
法院必然支持
AI替代就是违法解除
公司一定败诉
你的证据已经足够胜诉
通过检查
合法
没有风险
成功率80%
建议你马上仲裁
系统已经认定
```

也不得出现绿色的：

```text
PASS
ALL CHECKS PASSED
```

正确表达是：

> **在本工具当前覆盖的规则内，暂未发现明显冲突。该结果不等于解除合法，也不代表未覆盖事项不存在。**

# 七、每个定性终点的输出模板全文

## C00：操作尚未完成

### 操作尚未完成：现在是证据窗口，不是结论窗口

公司目前尚未完成解除或终止操作，因此本工具不能判断最终会采用哪一种法律路径。

现阶段最有价值的事情不是先计算 N 或 2N，而是把下列内容固定为书面记录：

* 你是否愿意续订或继续工作
* 公司所称岗位、团队或业务发生了什么变化
* 公司是否提出过具体调岗方案
* 双方谈的是岗位变更，还是只谈补偿和离职日期

### 最高优先级 Warning

**不要先提交"个人原因辞职"，也不要只用口头方式表达续订或继续工作的意愿。**

一旦公司正式作出操作，早期形成的文字可能直接影响解除主体、解除理由和举证方向。

### 下一步

在下一次回复、签字或交还设备前，先完成证据固定清单并导出本报告。

---

## C01：协商解除提议，尚未签署

### 当前更接近：公司提出协商解除，劳动关系尚未因该提议自动结束

公司提出补偿方案、离职日期或者协议草案，本身不等于你已经同意解除。

在你签署协商解除协议、提交个人辞职或者以其他方式明确接受前，当前仍处于谈判阶段。

### 最高优先级 Warning

**不要为了配合公司流程而提交"个人原因辞职"。**

个人辞职、公司提出协商解除和公司单方解除，是三种不同的法律事实。文件中的一句话，可能改变后续主张基础。

### 目前不建议做

* 不要把公司报价自动理解为法定应得金额
* 不要签署包含"双方再无任何争议"的文件后再期待工具自动恢复原有路径
* 不要只保存最终协议，忽略公司最初提出解除的聊天和邮件

---

## C02：已经签署或提交退出文件

### 自动判断已暂停：你签署或提交的文件可能已经改变解除性质

你已经签署协商解除协议、提交个人辞职，或者无法确认自己签署文件的性质。

此时不能仅根据公司此前做过什么来判断。需要同时审查：

* 文件标题和全部正文
* 谁先提出解除
* 签署过程
* 是否存在欺诈、胁迫或重大误解
* 款项是否已经支付
* 双方是否已经实际履行
* 文件是否包含放弃权利或无争议条款

### 最高优先级 Warning

**不要在没有审查原文件的情况下，再提交一份新的辞职说明、确认书或补充协议。**

追加文件可能进一步固化不利表述。

### 当前建议

先保留全部版本及签署过程记录，并使用 Case Export 向专业人士说明签署前后的完整时间线。

---

## C03：存在事实解除候选

### 当前存在：事实解除候选

你没有收到清晰的书面解除通知，但公司已经实施了部分拒绝用工行为，例如关闭权限、停止安排工作、禁止进入办公场所、停发工资或明确要求你不再到岗。

单一的账号关闭、移出群聊或者设备回收，不必然等于已经解除；需要结合多项行为、发生时间、公司表态以及你是否继续表达工作意愿综合判断。

### 最高优先级 Warning

**不要因为公司不安排工作，就自行停止到岗并长期保持沉默。**

如果条件允许，应当以合法、克制的书面方式表明：

> 我仍愿意按照劳动合同正常提供劳动，请公司明确劳动关系状态并安排工作。

### 当前定性

`事实解除`应当作为候选保留，但现有信息不足以直接认定已经发生违法解除。

---

## C04：普通合同到期终止及经济补偿候选

### 当前更接近：普通固定期限合同到期终止

在本工具覆盖范围内，暂未发现已经实际或视同连续订立二次固定期限合同的明确依据，也未发现依法必须续延的特殊状态。

如果公司没有提出以维持或提高原合同条件续订，或者提出的是降低条件的续订方案，普通到期终止可能产生经济补偿问题。

### 最高优先级 Warning

**普通到期终止不等于违法终止，也不能仅因公司不再续签就直接主张 2N。**

### 当前不支持的主张

仅凭"公司不续签"这一事实，当前不足以支持违法终止赔偿金候选。

仍需核对是否遗漏：

* 自动续延条款

# 十一、规则层数据结构

## 11.1 结论：YAML 作为法律规则源，TypeScript 负责执行，构建时生成 JSON

```text
YAML
= 律师可读、可审、可做 Git diff 的规则源

TypeScript + Zod
= 规则结构校验、日期计算和规则执行

Generated JSON
= 浏览器运行时读取的静态产物
```

### 不直接用 JSON 的原因

* 注释能力差
* 长篇依据、例外和证据要求可读性低
* 修改时逗号、括号噪声大
* 不利于律师直接审查 PR

### 不把规则全部写进 TypeScript 的原因

* 法律内容和执行代码耦合
* 改一段文案也需要进入代码文件
* PR 难以清楚显示"法律规则变了"还是"程序逻辑变了"
* 非程序员法律审核者不友好

### YAML 风险及处理

* 固定使用 YAML 1.2
* 日期全部加引号
* 禁止隐式布尔值
* 构建时拒绝重复键
* 每个规则必须通过 Zod Schema
* 构建失败时不允许部署

| T13 | 外部政策导致原业务依法无法继续；公司提出核心条件相当的具体岗位；真实协商失败；履行通知或代通知金 | C16，仅表述覆盖规则内未发现明显冲突 | |
| T14 | 公司提出具体岗位，但工资由 2.5 万元降至 1.5 万元并降低职级 | C15，方案合理性重大争议 | |
| T15 | 公司只说"你可以自己去内部招聘网站看看"，未明确岗位和条件 | C14，未形成实质性合同变更协商候选 | |

| T18 | 违法解除候选；未申请仲裁；劳动者明确不希望回去 | R02，赔偿金方向 | |

```markdown
# Employment Linter CN

> 在签署离职文件或提交仲裁请求前，检查合同到期、AI替岗和
> "客观情况发生重大变化"中的关键法律 warnings。

`NO UPLOAD` `NO APP TELEMETRY` `NO RUNTIME LLM`

**在线使用** · **查看规则** · **报告规则问题**

## What it checks

- 固定期限合同到期，是否可能触发"连续订立二次固定期限劳动合同"
- AI替岗、团队缩编或岗位取消，是否缺少第40条第3项的成立条件
- 继续履行、赔偿金和经济补偿之间是否可能选错主张路径
- 哪些证据现在还能取得，哪些会在账号关闭后消失
- 导出一份可交给任何律师的 Markdown Case Report

## What it does not do

This is a linter, not a verdict.

它不会：

- 判断你一定能赢
- 计算或承诺2N
- 生成仲裁申请书
- 上传、解析或保存劳动合同
- 用大模型读取你的案件
- 把"未命中规则"解释为解除合法

## Why the result is inspectable

每一条 Finding 都显示：

- Rule ID
- 依据条文
- 适用地域
- 生效时间
- 所需证据
- 例外
- 不确定性档位
- 对应测试用例

规则以 YAML 版本化，构建时校验，并通过公开测试用例回归。

> Star this repo as a bookmark before a signature, an HR reply,
> or an arbitration claim becomes difficult to change.
```

可信度来源不是"作者是专业律师"，而是：

* 没有黑箱大模型
* 规则可见
* 来源可核
* 不确定性显式
* 测试可复现
* 用户数据不进入系统

作者信息放到 README 很靠后的 `Maintainer`，不放首屏。

# 十八、高复杂度转化入口全文

仅在诊断完成且出现高复杂度触发条件时显示：

```text
## 建议进行专业复核

本次结果涉及以下一种或多种不可逆风险：

- 已经签署或提交退出文件；
- 已有仲裁请求可能与当前主张方向不一致；
- 继续履行与赔偿金路径尚未确定；
- 仲裁时效可能届满；
- 关键规则依赖个案事实或裁判评价；
- 存在本工具未覆盖的法定情形。

继续自行签字、回复或提交材料，可能把仍可调整的问题固定为程序记录。

建议在下一次行动前，由劳动法专业人士结合原始文件进行复核。

你可以先复制下方 Case Export，并交给任何你信任的律师。
```

按钮：

```text
[复制 Case Export]
[下载 Markdown]
[了解专业复核]
```

只有第三个按钮才进入律师信息页面。

不要写：

```text
立即添加陈律师
抢占咨询名额
专业律师一对一
成功维权
```

# 十九、最终的最小验收标准

v0.1 上线前必须同时达到：

1. 20 条自动测试全部通过
2. 现有一二十个匿名案件全部完成回放
3. 不出现任何全局 `PASS`
4. 不出现任何自动 2N 结论
5. 每个结果至少包含：定性候选、最高优先级 Warning、主张方向或停止判断、证据清单
6. 每个法律 Finding 都能展开看到 Rule ID、依据和生效日期
7. 在浏览器开发者工具中，填写答案期间不产生答案上报请求
8. 刷新页面后不恢复案件内容
9. Case Export 不默认包含姓名、身份证号和公司全称
10. 5—8 名程序员盲测后，至少大多数人能够准确说出：当前最可能的两种定性、现在最不能做的一件事、至少两项应立即保存的证据
11. 无人把页面结果理解为"已经确认违法"或"保证拿到 2N"
12. 至少 3—5 个未参与规则设计的真实案件没有出现严重漏报

# 二十、实际施工顺序

> **本节已被 round3 第十一节修订，以 round3 为准。**

真正的资产不是网页壳子，而是：

> **真实案件中反复出现的错误 → 最小纠错问题 → 显式规则 → 反向 Warning → 回归测试。**
