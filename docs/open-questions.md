## Q5 · 仲裁时效起算点 —— 已决（2026-09-04）

- **问题**：《劳动争议调解仲裁法》第二十七条第一款的一般起算点是
  "知道或者应当知道其权利被侵害之日"，而 round2 §4.7 P06 写的是
  "从解除或终止之日起"，两者不完全等同。
- **维护人答复**：该表述**更多指向在职期间的纠纷**；
  对于解除、终止类争议，原则上就是**离职后一年内**。
- **决定**：
  1. P06 的问法**保持不变**（从解除或终止之日起计算）。
  2. 该结论**只在解除/终止争议范围内成立**。规则 `CN-NAT-LDCA-27-LIMITATION`
     的 conditions 中用 `scope.dispute_category == TERMINATION_OR_EXPIRY`
     显式限定，并另设 `IN_SERVICE_DISPUTE` 例外阻断，防止引擎泛化到在职争议。
  3. 拖欠劳动报酬适用第二十七条第四款特别规则，而欠薪不在本工具覆盖范围
     （round2 §17 禁做清单），命中时转入 C18，不由时效规则处理
     （`WAGE_ARREARS_SPECIAL_RULE` 例外，effect: block）。
  4. "一年"按日历年计算，挂《民法典》第二百零二条，禁止实现为 365 天。

## Q7 · 规则例外（exceptions）尚未接入引擎（P3 发现）

- **现状**：`RuleRecord.exceptions[]` 目前只有 `id / description / effect` 三个字段，
  **没有条件表达式**，因此引擎无法自动判断某条例外是否命中。
- round2 §11.2 的原始结构就是这样定义的，不是实现遗漏。
- **P3 的处理**：引擎不做静默阻断（`blockedByException` 恒为 false）。
  例外目前靠问题树前置分流实现 —— 例如法定续延在 A05 就被路由到 C18，
  根本不会走到第十条第一项。T07 用例验证了这条路径。
- **需要维护人决定**：是否给 `exceptions[]` 增加 `conditions` 字段，
  让例外能被引擎自动求值。若增加，属于 schema 变更，需同步改
  `CN-NAT-LDCA-27-LIMITATION` 等已写了例外说明的规则。
- 在此之前，**任何新增例外都必须在问题树中有对应的前置分流**，
  否则该例外形同虚设。

## Q8 · 规格书原文自身含 §6.5 禁止表达（P4 发现，已按守卫优先处理）

- **问题**：round2 §6.5 明令禁止「通过检查」「合法」等表达，
  但 §7 的模板原文自己用到了它们：
  - C16「重要说明」首句：这不是"合法解除**通过检查**"。
  - C15：不会把"降低多少百分比"直接换算成**合法**或违法。
  - C19：不会在关键事实缺失时输出 N、2N 或者"**合法**解除"。
- **处理**：按 CLAUDE.md §P4，守卫测试对「通过检查」不设豁免，
  故三处均已最小改写，语义不变，并在模板的 `deviation_note` 中留档：
  - C16 →「这不是对解除的合规确认」
  - C15 →「直接换算成解除是否成立」
  - C19 →「输出 N、2N 或者解除已经成立的结论」
- 「合法」是裸词，会误伤"不代表解除合法""公司后来解除是否合法"这类
  **本产品必须说的话**，故按维护人 2026-09-03 的决定改用断言式搭配匹配
  （`属于合法` / `确认合法` / `认定为合法` / `已经合法`）。
- **需要维护人确认**：三处改写是否可接受，或指定其他措辞。
